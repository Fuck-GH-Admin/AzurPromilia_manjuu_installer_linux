> 编制日期：2026-11-25  
> 适用分支：main  
> 当前阶段：工作流代码已合并；完整游戏安装、真实版本更新与启动尚未完成端到端验收。  
> 本文是下一阶段的执行计划，不是已经完成的测试报告。

## 0. 目标与边界

目标是把当前已经实现的 \`info / install / verify / repair / preload / update\` 工作流，推进到可由真实官方元数据、真实 CDN 文件和可复核校验结果证明的可用状态。

本阶段优先完成“下载器完整链路”，不把游戏启动、Proton 调校或账号登录混入安装验收。只有安装目录、文件校验、版本状态和更新流程稳定后，才进入启动器集成。

### 必须遵守的证据边界

1. 官方 API、官方索引、官方 CDN 文件和真实版本变化，必须来自真实上游请求。
2. 本地单元测试可以验证路径处理、MD5、Range、文件替换、清理和状态机等确定性逻辑；不能用模拟服务器响应声称官方 API、官方 CDN 或真实版本更新已经通过。
3. 如果当前服务器没有 preload 版本、没有新旧版本差异，相关验收标记为“等待真实上游条件”，不制造假版本、不模拟服务端行为。
4. 所有首次全量安装、损坏修复和更新测试均使用独立、可丢弃的测试目录；不直接覆盖用户已有正式游戏目录。
5. 不删除旧 manifest 未追踪的文件，不自动清理用户未知内容。

## 2. 阶段 A：先修正文档与验收入口

### A1. 统一测试文档

- 将旧版 \`download\` 命令说明明确标注为底层/兼容入口。
- 区分 \`download --target preload\`（原始暂存下载）与新 \`preload\`（released/preload 差异比较）。
- 删除“CLI 尚无自动 downloadMode”“尚无预下载差异比较”等过期描述。
- 修复 shell 示例中错误的双反斜杠续行。
- 以本文件作为下一阶段的执行顺序，以 \`IMPLEMENTATION_STATUS.md\` 作为实现状态和最终验收勾选表。

### A2. 统一状态定义

每个事项只能使用以下状态之一：

- **代码已实现**：源码中存在对应路径。
- **自动化测试通过**：本地确定性测试或 CI 已通过。
- **官方小文件实测通过**：真实 API/CDN 索引和小资源校验通过。
- **官方全量实测通过**：真实完整安装/更新完成且全量校验通过。
- **待上游条件**：官方暂时没有可用 preload 或版本变化。
- **未实现**：尚无对应代码。

不得把前面任一状态自动升级成后面的状态。

## 3. 阶段 B：全量下载前的可靠性修正

先做不依赖大规模下载的代码工作，避免在全量任务中暴露已知可修复的问题。

### B1. Worker 错误处理

当前 \`runFiles\` 在某个文件失败后仍可能继续处理队列中的其他文件。下一步应：

- 首个不可恢复的文件错误出现时取消共享 context；
- 停止继续投递新任务；
- 等待正在运行的 worker 退出；
- 保留首个失败文件、路径、CDN 和 HTTP 错误；
- 重新运行时继续利用合法的 \`.part\` 断点文件。

验收：新增测试证明首错后停止新增请求；已有 Range 续传测试继续通过。

### B2. 磁盘空间预检查

在下载/解压前计算可证明的空间需求：

- REALITY：统计缺失或校验失败文件的大小，不把已校验文件重复计入。
- SLICE：统计待下载分片、合并 ZIP 和 ZIP 解压所需空间；不能只按压缩包大小判断。
- PRELOAD：统计尚未存在且 MD5 不匹配的差异文件。
- UPDATE：考虑正式目录、预下载暂存和合并/临时文件可能同时占用的空间。

空间不足时应在大规模下载前明确报错，列出需求估算与可用空间。估算无法覆盖的文件系统保留空间、配额或并发写入风险必须注明。

### B3. ZIP 与文件系统保护

- 在所有 ZIP 解压入口统一执行条目路径、重复路径、符号链接和保留目录检查。
- 统计 ZIP 中央目录声明的总解压大小并防止整数溢出。
- 设计有依据的解压大小上限/磁盘空间保护，不随意使用可能误伤正常游戏资源的压缩比阈值。
- 检查解压失败后的临时文件清理与重试行为。
- 为根目录、索引目录、暂存目录和 manifest 路径补充符号链接回归测试。

### B4. 更新失败语义

当前更新是逐文件原子替换，不是整次升级事务回滚。短期先明确并测试“失败后继续向前收敛”的策略：

- 文件级下载、校验、rename 成功后才替换目标文件；
- 全部新文件校验成功后才清理旧 manifest 追踪文件；
- 全部必要步骤完成后才更新版本标记；
- 失败后再次执行 update 可以继续完成；
- 明确提示更新未完成期间不要启动游戏。

本阶段不默认引入整目录备份/全局回滚，因为大型游戏目录的备份成本可能不可接受。是否增加事务日志或回滚机制，依据真实失败场景再决定。

## 4. 阶段 C：真实官方元数据与首次完整安装

### C1. 先获取当前真实元数据

运行：

\`\`\`bash
./azurpromilia info --installer /path/to/original.exe
\`\`\`

记录并脱敏保存：

- 请求时间、API 主/备用站结果；
- released/preload 的 versionCode、versionName；
- downloadMode；
- 每种 packageType 是否存在、索引大小、CDN 主机名；
- gameFolderName、launchEntry；
- config 与 pre/check 是否成功，失败时保留 HTTP/API 错误码，不猜测。

不要提交完整 CDN 临时 URL、签名、secretKey、token 或设备标识。

### C2. 执行服务端选定模式的首次安装

优先使用 \`--mode auto\`，让程序依据本轮真实 \`downloadMode\` 选择包类型。测试目录必须为空且可丢弃。

REALITY 模式验收：
- 官方 packageType 2 索引下载、解密、解析成功；
- 40,457 文件/实际本轮索引记录数与计数头一致；
- 所有文件完成下载或复用后逐个 MD5/大小校验；
- 最终 verify 全部通过；
- \`_index/<version>\`、\`_index/version\`、manifest 版本和文件数一致。

SLICE 模式验收：
- 官方 packageType 1 的全部分片下载并校验；
- 按原始索引顺序合并；
- 最终 ZIP 的大小与 MD5 匹配；
- ZIP 条目检查通过；
- 解压完成后逐文件 CRC32/大小校验全部通过；
- 若服务器同时提供 type-2 索引，确认其被正确保存为后续版本管理基线；若不可用，记录降级状态和限制。

### C3. 额外包类型兼容验证

自动模式完整安装通过后，再判断是否值得对另一种包类型做第二套全量测试。若另一种模式需要额外大量空间或下载成本，先用已有官方小文件探测和代码检查，不为了形式重复下载整套游戏。

## 5. 阶段 D：修复、预下载与升级

### D1. Repair（可以在当前版本验证）

在独立测试安装目录中选择一个已由 manifest 追踪的普通资源文件：

1. 记录原文件大小和 MD5；
2. 只在可丢弃测试目录中破坏或移走该文件；
3. 执行 \`repair\`；
4. 确认文件重新获取且 MD5 恢复；
5. 再执行完整 \`verify\`；
6. 确认 repair 不清理旧版本文件、不覆盖排除文件。

不得在用户正式游戏目录做破坏性测试。

### D2. Preload（依赖真实 preload 数据）

只有官方响应提供不同于 released 的 preload 版本时才执行：

1. 记录两份真实索引的版本和文件计数；
2. 比较相对路径与 MD5；
3. 下载新增/变化文件；
4. 验证暂存 manifest 中所有文件；
5. 记录下载字节数与理论差异字节数；
6. 若没有 preload 或 preload 与 released 相同，记为“待上游条件”，不构造假数据代替。

### D3. Update（依赖真实版本差异）

只有安装目录版本确实低于官方 released 时才执行：

1. 读取旧版本 manifest/官方索引；
2. 获取新版本官方 type-2 索引；
3. 验证并复用对应新版本的预下载文件；
4. 下载其他缺失或变化资源；
5. 校验所有新版本文件；
6. 清理旧 manifest 追踪且新版本不存在的文件；
7. 保留排除文件、未知文件和用户数据；
8. 最后更新版本标记；
9. 最终 verify 全部通过。

如果没有真实的新旧版本差异，不以本地手工改版本号的方式声称更新验收成功。

## 6. 阶段 E：启动信息与 Proton（下载链路之后）

本阶段不与安装验收混为一谈：

- 检查匿名 \`config\`、\`pre/check\` 是否返回真实 launchEntry、launchParams、gameRuntimeParams。
- 结合已安装目录确认真实 EXE 路径，不能仅凭字段名猜启动入口。
- 明确哪些参数是原版 Windows 启动器注入、哪些可以在 Linux/Proton 下使用。
- 再建立独立 Proton 前缀做启动实验，记录发行版、显卡驱动、Proton 版本、日志和失败点。
- 不修改游戏文件、反作弊或账号环境，不把“下载完成”说成“游戏可运行”。
